# 2026-08-12 会话列表首屏加载性能与 RBAC 缓存修复重点案例

## 1. 案例背景

这是一次从线上现象出发的首屏性能与权限一致性修复。用户反馈：

- 管理员登录进入 chat 页面后，左侧会话列表约 7 秒才加载完成。
- 多用户切换后存在缓存残留风险：无 workspace 用户切到有 workspace 用户、有 workspace 用户切到无 workspace 用户、删除唯一 workspace 后都必须严格清空旧状态。
- 重点风险不是单纯慢，而是慢请求和账号切换叠加后可能让旧用户的 session/workspace 数据短暂出现在新用户界面。

安全约束：本案例不记录任何登录凭据、Cookie、token、真实私有路径或可复用的生产访问细节。

## 3. 溯源思考

第一反应不能只看“7 秒”这个结果。这里同时有三类风险：

1. **性能风险**：管理员可见 session 多，首屏 session list 如果扫描全量 state.db，会直接拖慢 UI。
2. **权限风险**：RBAC 场景下，慢请求可能跨账号切换晚到，覆盖新账号 UI。
3. **状态风险**：workspace 为空、唯一 workspace 删除、BFCache 恢复都容易被本地缓存和 fallback 逻辑污染。

因此排查顺序不是先盲目加 timeout，而是先拆链路：

- 浏览器启动时哪些请求串行，哪些可以并行。
- `/api/sessions` 后端阶段分别耗时多少。
- 账号身份何时确定，session list 何时允许渲染。
- 空 workspace 是否被 last workspace fallback 覆盖。
- 删除 workspace 后 composer、文件树、缓存是否同步清空。

## 4. 发现的问题

### 4.1 前端启动串行化

原启动路径在 auth、settings、session list、workspace list、profile warmup、shared-session warmup 之间有不必要等待。对于 admin 用户，哪怕后端能较快返回，session list 请求也可能被 settings/profile 初始化阻塞。

修复思路：

- 先启动 `/api/auth/status`。
- 在 WebUI tab 且安全条件满足时提前启动 `/api/sessions`。
- `/api/settings`、`/api/projects`、workspace list 并行推进。
- profile dropdown 和 shared sessions 延后到 `hermes:session-list-ready` 后再启动。

### 4.2 RBAC 身份与在途请求竞争

账号切换或 BFCache 恢复后，旧账号的 `/api/sessions` 响应可能晚到。只靠 localStorage 的 session list cache 不够，因为真正危险的是“响应回来时当前账号已经变了”。

修复思路：

- auth identity 增加短 TTL snapshot，减少重复 `/api/auth/status`。
- session list 刷新支持 `authScopeReady`，请求可提前发出，但落 UI 前必须等待身份确认。
- 使用 render generation 丢弃旧响应。
- 如果 auth scope 在请求期间变化，主动排队 refetch。
- login 存储 auth role hint，让 admin 首次请求在 auth 状态完全返回前也能带上 `limit=120`。

### 4.3 后端首屏预算无界

慢点集中在：

- state.db 对 messages 做 count/max 聚合。
- lineage metadata 读取又重复查询 message stats。
- delegated subagent 判断可能按行探测 state.db，形成 N+1。
- SQLite 被其它写入持锁时，sidebar 读等待时间过长。

修复思路：

- `/api/sessions?limit=120` 进入 cache key，避免和无限列表共用缓存。
- `all_sessions(..., state_db_override_top_n=120)` 将首屏 COUNT/MAX 聚合限制到可见预算。
- state.db override 读取出的 message stats 传给 lineage 复用。
- subagent coercion 复用同一份 state.db source metadata，避免逐行重开 SQLite。
- sidebar 专用 state.db/lineage 读设置 50ms busy timeout，锁竞争时 fail-open 到 sidecar 数据；普通 lineage 调用仍保持默认完整语义。

### 4.4 测试环境 license gate 干扰

提交收口时，staged snapshot 测试暴露：

- `/health` 被 license gate 返回 403，测试服务器无法启动。
- route handler 内部重复 license gate，focused route tests 被提前 403。
- 真实 server POST `/api/settings` 在测试环境 license 未激活时返回 503。

修复思路：

- `/health` 加入 license whitelist。
- `server.py` 已统一在 dispatch 前做 license middleware，`handle_get/handle_post` 保持可被 focused tests 直接调用。
- test server state 写入测试专用 activated license，避免 POST route tests 测的是中间件失败而不是产品代码。

## 7. 关键经验

1. **性能问题要先分阶段计时**  
   这次不是“网络慢”，而是首屏请求串行化和 state.db 无界读取叠加。没有阶段耗时，容易误改 timeout。

2. **RBAC 场景下慢请求就是权限风险**  
   请求晚到不是单纯 UI 问题。账号切换后，旧响应必须按 generation 和 auth scope 丢弃。

3. **首屏只读可接受降级，详情页读不能降级**  
   sidebar 是导航索引，锁竞争时可以 fail-open 到 sidecar；真正打开 lineage/detail 时仍要完整读取。

4. **cache key 必须携带所有影响可见结果的参数**  
   `limit`、RBAC user、sidebar source、profile scope 都必须进入 key，否则会出现跨范围复用。

5. **测试要验证 staged snapshot**  
   本次工作区有未提交的本地化/license 改动。用临时 staged snapshot 测试，避免把未提交代码当作提交质量。

6. **提交前要检查混合文件**  
   `static/sessions.js`、`static/login.js`、`tests/test_session_share_ui.py` 同时有相关和无关 hunk。必须拆开暂存，避免把本地化/管理端杂项混进性能提交。

## 8. 后续建议

- 增加线上性能自动化基线：记录 auth/settings/projects/sessions 的 start/end、TTFB、response size、render-ready 时间。
- 为 `/api/sessions?limit=N` 增加浏览器 E2E 断言：首屏 rows 限制生效，但 counts 保持全量。
- 将 RBAC account switch 场景加入固定 smoke：旧账号慢响应晚到时不得更新 sidebar/workspace。
- 长期方案仍应推进 session sidebar index/materialized projection，避免每次首屏都依赖大 state.db 的即时聚合。
