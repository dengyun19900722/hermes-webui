# 2026-08-14 后台模型检测与知识库超时红色 Toast 故障修复

## 1. 背景

线上页面频繁弹出红色英文 toast：

```text
Request timed out. Please try again.
```

用户反馈该提示像“异常报错”，但无法判断是否为模型服务连不上、后台扫描了其它模型，还是知识库页面自身加载慢。该提示还带有 `Copy` / `Dismiss` 操作，视觉级别接近致命错误，影响正常阅读知识库内容。

安全约束：本文不记录线上账号密码、Cookie、token、完整请求头或可复用私有凭据。线上地址只作为现场排查入口，不固化敏感登录信息。

## 2. 影响范围

影响场景：

- 打开 WebUI 后进入 Knowledge 页面。
- 恢复上次会话时，前端后台补水当前会话模型信息。
- 顶部 reasoning chip 后台探测当前模型是否支持 reasoning effort。
- 知识库目录树扫描或正文读取超时。

用户可见症状：

- 页面右上角连续弹出多个红色英文 `Request timed out. Please try again.`。
- Knowledge 左侧列表出现 `加载知识库失败：Request timed out. Please try again.`。
- 用户无法从提示判断是模型问题、知识库扫描问题，还是普通网络问题。
- 同一轮页面加载中可能出现多个相同红色 toast，造成“系统异常”的误判。

## 3. 线上复现与证据

使用 ego-browser 在线上页面注入临时诊断脚本：

1. 包装 `window.fetch`，记录 URL、HTTP 状态、耗时、AbortError。
2. 包装 `window.showToast`，记录 message、duration、type。
3. 点击 Knowledge。
4. 等待 36 秒，覆盖前端默认 30 秒超时窗口。
5. 读取 `window.__hermesFetchLog` 和 `window.__hermesToastLog`。

关键结论：

  - 两个 `/api/reasoning` 后台模型能力探测。
  - 一个 `/api/session?...resolve_model=1` 延迟模型信息补水。
  - 一个 `/api/notes/tree` 知识库目录扫描。
- 这些都是可降级读操作，不应该使用红色致命错误 toast。

## 4. 根因

### 4.1 `api()` 的默认超时提示过于通用

`static/workspace.js` 中的通用 `api()` 包装器在请求超过默认 30 秒时会统一弹：

```text
Request timed out. Please try again.
```

该文案没有接口上下文，也没有中文说明。只要调用方没有设置 `timeoutToast:false`，超时都会被当成红色 error toast。

### 4.2 后台模型探测没有关闭默认 timeout toast

`fetchReasoningChip()` 用于判断当前模型是否支持 reasoning effort。它属于 UI 辅助能力探测：

- 成功：展示 reasoning chip。
- 失败：隐藏或降级即可。

但原实现直接调用：

```javascript
api('/api/reasoning' + key)
```

当模型服务响应慢、provider 探测阻塞或后端繁忙时，该请求会触发默认红色 timeout toast。

### 4.3 `resolve_model=1` 是延迟补水，不应打断阅读

`_resolveSessionModelForDisplaySoon()` 在会话首屏后延迟请求：

```text
/api/session?messages=0&resolve_model=1
```

它的用途是补齐展示用模型、provider、context length 等信息。首屏会话已经通过 `resolve_model=0` 加载，延迟补水失败不应影响当前页面可用性。

但原请求没有设置 `timeoutToast:false`，因此后台失败也会弹红色 toast。

### 4.4 Knowledge 目录扫描超时缺少业务化提示

Knowledge 页面读取：

```text
/api/notes/tree
/api/notes/search
/api/notes/content
```

这些是知识库读路径。超时原因更可能是：

- 知识库目录较大，后端正在扫描。
- 磁盘或服务繁忙。
- 正文文件较大。

原实现把 timeout 的英文 `e.message` 直接展示到 toast 或列表中，用户看不到“知识库目录扫描”这个关键上下文。

## 5. 修复内容

### 5.1 新增一次性 warning helper

文件：`static/ui.js`

新增：

- `isRequestTimeoutError(e)`：统一识别 `TimeoutError` / `timeout=true` / timeout 文案。
- `showWarningOnce(key, msg, ms, ttlMs)`：同一类 warning 在默认 60 秒内只展示一次。

作用：

- 避免 `/api/reasoning`、`resolve_model=1` 在同一页面加载周期内重复刷屏。
- 保留 warning 级别，降低误报为“系统崩溃”的风险。

### 5.2 `/api/reasoning` 改为后台短预算与中文 warning

文件：`static/ui.js`

修复后：

```javascript
api('/api/reasoning'+key,{timeoutMs:8000,timeoutToast:false,retries:0})
```

超时时提示：

```text
模型状态检测超时：当前模型服务响应慢，或后台正在探测模型能力。已暂时使用缓存信息，不影响继续浏览页面。
```

该 warning 使用 `model-status-timeout` key 去重。

### 5.3 `resolve_model=1` 延迟补水关闭默认红 toast

文件：`static/sessions.js`

修复后：

```javascript
api(
  `/api/session?session_id=${encodeURIComponent(sid)}&messages=0&resolve_model=1`,
  {timeoutMs:8000,timeoutToast:false,retries:0}
)
```

超时时复用 `model-status-timeout` warning，不再弹出额外红色 toast。

### 5.4 Knowledge 读路径改为业务化中文 warning

文件：`static/obsidian_notes.js`

修复点：

- `/api/notes/tree` 关闭默认 timeout toast。
- `/api/notes/search` 关闭默认 timeout toast。
- `/api/notes/content` 关闭默认 timeout toast。
- 超时后显示具体中文 warning。

新增提示：

```text
知识库目录加载超时：后端可能正在扫描较大的知识库，或当前服务繁忙。请稍后点击刷新。
知识库搜索超时：后端可能正在扫描目录或检索范围较大，请缩小关键词后重试。
笔记正文加载超时：后端可能正在读取大文件或当前服务繁忙，请稍后重试。
```

文件：`static/style.css`

新增 `.knowledge-warning`，使用 `var(--warning)` 区分 warning 与 error。

## 6. 修复后预期行为

同样的线上慢请求场景，用户不再看到 4 个红色英文错误。

预期变为最多两个黄色中文 warning：

1. 模型状态检测超时：
   - 覆盖 `/api/reasoning` 和 `resolve_model=1`。

用户仍可继续浏览当前页面。模型状态补水和 reasoning chip 能在后续同步中重试。

## 8. 人工排查线上同类问题步骤

### 8.1 浏览器侧确认哪个请求触发 toast

在浏览器控制台临时注入：

```javascript
window.__hermesFetchLog = [];
window.__hermesToastLog = [];

const originalFetch = window.fetch;
window.fetch = function(input, init) {
  const url = typeof input === 'string' ? input : (input && input.url) || String(input);
  const method = (init && init.method) || (input && input.method) || 'GET';
  const start = performance.now();
  return originalFetch.apply(this, arguments).then(res => {
    window.__hermesFetchLog.push({
      url,
      method,
      ok: res.ok,
      status: res.status,
      ms: Math.round(performance.now() - start)
    });
    return res;
  }, err => {
    window.__hermesFetchLog.push({
      url,
      method,
      error: (err && (err.name + ': ' + err.message)) || String(err),
      ms: Math.round(performance.now() - start)
    });
    throw err;
  });
};

const originalToast = window.showToast;
window.showToast = function(message, duration, type) {
  window.__hermesToastLog.push({
    message: String(message),
    duration: duration == null ? null : duration,
    type: type || null,
    ts: Date.now()
  });
  return originalToast.apply(this, arguments);
};
```

复现后执行：

```javascript
({
  toasts: window.__hermesToastLog,
  slowFetches: window.__hermesFetchLog.filter(x => x.ms > 5000 || x.error)
})
```

重点看：

- 是否仍有 `Request timed out. Please try again.`。
- `type` 是否仍为 `error`。
- 超时 URL 是否为后台可降级读接口。

### 8.2 服务端日志排查建议

如果 warning 仍频繁出现，需要继续查服务端性能：

1. 查 `/api/reasoning` 是否被模型 provider 探测拖慢。
2. 查 `/api/session?...resolve_model=1` 是否卡在 `resolve_model_provider`。
3. 查 `/api/notes/tree` 是否因知识库文件过多、目录递归或磁盘 I/O 慢导致超时。
4. 对比 `/api/models` 耗时，避免误判为主模型目录扫描。

建议记录字段：

- endpoint。
- status。
- elapsed ms。
- active profile。
- model/provider。
- 是否命中 cache。
- 知识库 note count / tree scan count。

不要记录：

- API key。
- Cookie。
- Authorization header。
- 用户明文密码。
- 完整 `.env` 或 `auth.json`。

## 9. 后续观察项

本次修复主要解决“可降级后台请求被展示成红色英文异常”的重大体验缺陷。它不等价于完全解决后端慢请求。

后续需要继续观察：

- `/api/notes/tree` 是否经常超过 30 秒。
- `/api/profiles` 是否接近 30 秒边界。
- `/api/session?messages=1&resolve_model=0` 是否长期接近 30 秒。
- `/api/reasoning` 是否需要服务端缓存或更短 provider 探测预算。
- Gateway heartbeat banner 与本次 toast 是两个问题，需单独排查。

部署后验收标准：

- Knowledge 页面不再出现红色英文 `Request timed out. Please try again.`。
- 慢模型检测只出现一次黄色中文 warning。
- 知识库目录慢时，左侧列表显示中文原因和可执行建议。
- Chat 阅读、Knowledge 阅读不被后台模型探测打断。
